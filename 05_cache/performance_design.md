# Домашнее задание 05: Оптимизация производительности через кеширование и rate limiting
**Вариант 20:** Система управления медицинскими записями

---

## 1. Анализ производительности
- **Горячие пути (Hot Paths)**
  - `GET /api/v1/patients/search` — поиск пациентов по ФИО (высокая частота запросов от врачей и регистратуры)
  - `GET /api/v1/patients/{id}/records` — получение истории медицинских записей (открывается при каждом приёме пациента)
  - `GET /api/v1/records/{code}` — получение записи по уникальному коду (справочные операции)
- **Медленные операции**
  - Поиск по маске: использование `ILIKE '%value%'` требует сканирования индексов, время выполнения растёт с увеличением объёма таблицы `patients`
  - История записей: `JOIN` таблиц `medical_records` и `patients` с фильтрацией по дате и статусу, генерация JSON-ответа на лету
  - Внешние интеграции: проверка страхового полиса и отправка уведомлений (сетевые задержки, возможные таймауты сторонних сервисов)
- **Требования к производительности**
  - Время отклика: `< 200 мс` для 95-го перцентиля (p95)
  - Пропускная способность: `≥ 100 RPS` на один инстанс приложения
  - Отказоустойчивость: `99.9%`, graceful degradation при недоступности оптимизационных модулей

---

## 2. Проектирование стратегии кеширования
- **Данные для кеширования**
  - Часто читаемые: история записей пациента, результаты поиска по ФИО
  - Результаты сложных вычислений: агрегированные списки пациентов с фильтрацией
  - Редко изменяемые: данные конкретной медицинской записи по коду (историческая справка не редактируется после создания)
- **Стратегия кеширования**
  - Выбрана **Cache-Aside (Lazy Loading)**. Приложение самостоятельно проверяет кеш. При отсутствии данных запрашивает БД, сохраняет результат в кеш и возвращает клиенту. Паттерн оптимален для read-heavy сценариев и изолирует бизнес-логику от состояния кеша.
- **TTL (Time To Live)**
  - Поиск по ФИО: `300 сек` (баланс между свежестью данных и нагрузкой на БД)
  - История записей пациента: `120 сек` (данные меняются не чаще нескольких раз в день)
  - Запись по коду: `600 сек` (статичные исторические данные)
- **Стратегия инвалидации**
  - Явная инвалидация при мутациях: `del()` для конкретных ключей после успешного `COMMIT` в БД
  - Паттерн-инвалидация: `invalidatePattern("patient:search:")` при создании нового пациента, чтобы сбросить устаревшие списки поиска
  - Синхронное выполнение в рамках транзакции обработки запроса гарантирует eventual consistency

---

## 3. Реализация кеширования
- **Техническая реализация**
  - Потокобезопасный in-memory кеш на базе `std::unordered_map<std::string, CacheEntry>` + `std::mutex`. `CacheEntry` хранит JSON-строку и метку времени истечения (`expiresAt`). При чтении автоматически проверяется TTL и удаляются просроченные записи.
- **Применение к endpoints**
  1. `GET /api/v1/patients/search?firstName=...` (ключ: `patient:search:{params}`, TTL: 300s)
  2. `GET /api/v1/patients/{id}/records` (ключ: `patient:{id}:records`, TTL: 120s)
- **Инвалидация при обновлении**
  - `POST /api/v1/patients` → вызов `g_cache->invalidatePattern("patient:search:")`
  - `POST /api/v1/patients/{id}/records` → вызов `g_cache->del("patient:{id}:records")`
  - Инвалидация выполняется строго после успешной записи в PostgreSQL

## 4. Проектирование rate limiting
- **Endpoints, требующие ограничения**
  - `GET /api/v1/patients/search` — высокая нагрузка при сканировании/переборе, риск DoS
  - `GET /api/v1/patients/{id}/records` — ресурсоёмкие JOIN-запросы, риск истощения пула соединений БД
- **Алгоритм**
  - **Fixed Window Counter**. Ключ формируется как `rl:{endpoint}:{client_ip}`. Счётчик запросов инкрементируется в памяти. При достижении лимита в рамках 60-секундного окна запрос блокируется. Окно автоматически сбрасывается при истечении TTL. Алгоритм выбран за O(1) сложность проверки, минимальное потребление памяти и простоту масштабирования.
- **Лимиты**
  - Обычные пользователи: `60 запросов/мин` для поиска, `100 запросов/мин` для истории записей
  - Премиум/врачи: лимиты могут быть увеличены в 5x через параметр `limitOverride` при проверке, в зависимости от роли из JWT-токена

---

## 5. Реализация rate limiting
- **Интеграция**
  - Проверка лимита выполняется в начале `handleRequest` до обращения к сервисному слою и БД. При превышении лимита выполнение обработчика прерывается (short-circuit).
  - Реализован fail-open режим: при ошибке инициализации лимитера система продолжает работу без ограничений, чтобы не блокировать легитимный трафик.
- **HTTP статус-коды и заголовки**
  - При превышении лимита возвращается `429 Too Many Requests`
  - В каждый ответ добавляются стандартные заголовки:
    - `X-RateLimit-Limit`: максимальное количество запросов в окне
    - `X-RateLimit-Remaining`: количество оставшихся запросов
    - `X-RateLimit-Reset`: время (в секундах) до сброса счётчика
    - `Retry-After`: указывается только при ответе `429`

## 6. Анализ производительности
- **Влияние оптимизаций на систему**
  - **Кеширование**: снижает нагрузку на PostgreSQL на ~60-80% при повторяющихся запросах. Время отклика падает с ~120 мс (сетевой запрос + диск) до <5 мс (доступ к RAM). Уменьшает contention в пуле соединений.
  - **Rate Limiting**: защищает БД и пул потоков от всплесков трафика и неоптимальных клиентских скриптов. Стабилизирует p95 latency, предотвращает каскадные отказы и обеспечивает fair-use политику для всех потребителей API.
- **Метрики для мониторинга производительности**
  ```yaml
  cache_metrics:
    - hit_rate: hits / (hits + misses)
    - miss_rate: 1 - hit_rate
    - active_keys: количество непросроченных записей в памяти
    - eviction_rate: количество удалённых записей по TTL в минуту
  rate_limit_metrics:
    - 429_responses_count: количество заблокированных запросов
    - avg_window_usage: среднее заполнение окна запросами
  infra_metrics:
    - response_time_p95 / p99
    - requests_per_second (RPS)
    - db_query_time_avg
  ```
- **Измерение эффективности кеширования (hit rate)**
  - Логирование ведётся на уровне `CacheService::get()` через `Poco::Logger` с метками `CACHE_HIT` / `CACHE_MISS`
  - Формула: `Hit Rate = CACHE_HIT / (CACHE_HIT + CACHE_MISS) * 100%`
  - Сбор метрик в production:
    ```bash
    docker compose logs api | grep -E "CACHE_HIT|CACHE_MISS" | awk '{print $1}' | sort | uniq -c
    ```
  - Целевой показатель для read-heavy медицинской системы: `70-85%`. При падении ниже 50% рекомендуется пересмотр TTL или внедрить паттерн Write-Through для часто обновляемых справочников.
