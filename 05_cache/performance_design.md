## 1. Анализ производительности
- **Горячие пути (Hot Paths)**
  - `GET /api/v1/patients/search` — поиск пациентов по ФИО (частые запросы от врачей и регистратуры)
  - `GET /api/v1/patients/{id}/records` — получение истории медицинских записей (открывается при каждом приёме)
- **Медленные операции**
  - Поиск по маске: `ILIKE '%value%'` требует сканирования B-tree/GIN индексов, время выполнения линейно зависит от объёма таблицы `patients`
  - История записей: `JOIN` таблиц `medical_records` и `patients` с фильтрацией по дате, генерация JSON на лету
  - Внешние интеграции: проверка страхового полиса, отправка уведомлений (сетевые задержки, риск таймаутов)
- **Требования к производительности**
  - Время отклика: `< 200 мс` для 95-го перцентиля (p95)
  - Пропускная способность: `≥ 100 RPS` на один инстанс приложения
  - Доступность: `99.9%`, graceful degradation при недоступности модулей оптимизации

## 2. Проектирование стратегии кеширования
- **Какие данные кешировать**
  - Часто читаемые: история записей пациента, результаты поиска по ФИО
  - Результаты сложных вычислений: агрегированные списки с фильтрацией
  - Редко изменяемые: конкретная медицинская запись по коду (историческая справка не редактируется после создания)
- **Выбранная стратегия**
  - **Cache-Aside (Lazy Loading)**. Приложение самостоятельно проверяет кеш. При отсутствии данных запрашивает БД, сохраняет результат в кеш и возвращает клиенту. Оптимален для read-heavy сценариев, изолирует бизнес-логику от состояния кеша.
- **TTL (Time To Live)**
  - Поиск по ФИО: `300 сек`
  - История записей пациента: `120 сек`
  - Запись по коду: `600 сек`
- **Стратегия инвалидации**
  - Явная инвалидация при мутациях: `del()` для конкретных ключей после успешного `COMMIT` в БД
  - Паттерн-инвалидация: `invalidatePattern("patient:search:")` при создании пациента, чтобы сбросить устаревшие списки поиска
  - Синхронное выполнение гарантирует eventual consistency

---

## 3. Реализация кеширования
- **Техническая реализация**: Потокобезопасный in-memory кеш на базе `std::unordered_map` + `std::mutex`. Автоматическая проверка TTL при чтении, удаление просроченных записей.
- **Применение к ≥2 endpoints**:
  1. `GET /api/v1/patients/search?firstName=...` (ключ: `patient:search:{params}`, TTL: 300s)
  2. `GET /api/v1/patients/{id}/records` (ключ: `patient:{id}:records`, TTL: 120s)
- **Инвалидация при обновлении**: Выполняется строго после успешной записи в PostgreSQL. `POST /patients` → инвалидация паттерна поиска. `POST /patients/{id}/records` → инвалидация ключа истории пациента.

## 4. Проектирование rate limiting
- **Endpoints, требующие ограничения**
  - `GET /api/v1/patients/search` — риск DoS при переборе параметров, высокая нагрузка на индексы
  - `GET /api/v1/patients/{id}/records` — ресурсоёмкие JOIN-запросы, риск истощения пула соединений БД
- **Выбранный алгоритм**: **Fixed Window Counter**. Ключ: `rl:{endpoint}:{client_ip}`. Счётчик инкрементируется в памяти. При достижении лимита в рамках окна запрос блокируется. Окно сбрасывается по истечении TTL. Выбран за O(1) сложность, минимальное потребление RAM и предсказуемость.
- **Лимиты**
  - Обычные пользователи: `60 запросов/мин` для поиска, `100 запросов/мин` для истории записей
  - Премиум-пользователи/врачи: `300` и `500 запросов/мин` соответственно (реализуется через переопределение лимита при валидации JWT-роли)

---

## 5. Реализация rate limiting
- **Интеграция**: Проверка лимита выполняется в начале `handleRequest` до обращения к сервисному слою. При превышении выполнение прерывается (short-circuit).
- **HTTP статус-коды и заголовки**
  - При превышении лимита возвращается `HTTP 429 Too Many Requests`
  - В каждый ответ добавляются стандартные заголовки:
    - `X-RateLimit-Limit: 60`
    - `X-RateLimit-Remaining: 42`
    - `X-RateLimit-Reset: 38`
    - `Retry-After: 38` (указывается только при ответе `429`)
- **Fail-open**: При ошибке инициализации лимитера система продолжает работу без ограничений, чтобы не блокировать легитимный трафик.

## 6. Анализ производительности
- **Влияние оптимизаций на систему**
  - **Кеширование**: Снижает нагрузку на PostgreSQL на ~60–80% при повторяющихся запросах. Время отклика падает с ~120 мс (сеть + диск) до `<5 мс` (оперативная память). Уменьшает contention в пуле соединений.
  - **Rate Limiting**: Защищает БД и пул потоков от всплесков трафика.
