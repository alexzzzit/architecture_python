## 1. Анализ производительности

### Горячие пути (часто используемые операции)
- `GET /api/v1/patients/search` — поиск пациентов по ФИО (высокая частота запросов от врачей и регистратуры)
- `GET /api/v1/patients/{id}/records` — получение истории медицинских записей (открывается при каждом приёме пациента)

### Медленные операции
- **Поиск по маске**: использование `ILIKE '%value%'` требует сканирования индексов, время выполнения растёт с увеличением объёма таблицы `patients`
- **История записей**: `JOIN` таблиц `medical_records` и `patients` с фильтрацией по дате, генерация JSON-ответа на лету
- **Внешние интеграции**: проверка страхового полиса и отправка уведомлений (сетевые задержки, возможные таймауты сторонних сервисов)

### Требования к производительности
- Время отклика: `< 200 мс` для 95-го перцентиля (p95)
- Пропускная способность: `≥ 100 RPS` на один инстанс приложения
- Доступность: `99.9%`, поддержка graceful degradation при недоступности модулей оптимизации

## 2. Стратегия кеширования

### Данные для кеширования
| Тип данных | Характеристика | Стратегия | TTL |
|------------|----------------|-----------|-----|
| Результаты поиска по ФИО | Часто читаются, редко меняются | Cache-Aside | 300s |
| История записей пациента | Открывается много раз за сеанс | Cache-Aside | 120s |
| Конкретная запись по коду | Историческая справка, не редактируется | Cache-Aside | 600s |

### Выбор стратегии: Cache-Aside (Lazy Loading)
- Приложение самостоятельно проверяет кеш перед обращением к БД
- При отсутствии данных: запрос к БД → сохранение в кеш → возврат клиенту
- Преимущества: простая отладка, явный контроль инвалидации, изоляция бизнес-логики от состояния кеша

### Стратегия инвалидации
- Явная инвалидация при мутациях: `del()` для конкретных ключей после успешного `COMMIT` в БД
- Паттерн-инвалидация: `invalidatePattern("patient:search:")` при создании нового пациента
- Синхронное выполнение гарантирует eventual consistency

## 3. Реализация кеширования

### Техническая реализация
- In-memory кеш на базе `std::unordered_map<std::string, CacheEntry>` + `std::mutex`
- Каждая запись хранит значение (JSON-строка) и время истечения (`expiresAt`)
- При чтении автоматически проверяется TTL, просроченные записи удаляются

### Применение к эндпоинтам
| Endpoint | Ключ кеша | TTL |
|----------|-----------|-----|
| `GET /api/v1/patients/search` | `patient:search:{params}` | 300s |
| `GET /api/v1/patients/{id}/records` | `patient:{id}:records` | 120s |

### Инвалидация в коде
```cpp
// После успешного создания пациента
g_cache->invalidatePattern("patient:search:");

// После добавления записи
g_cache->del("patient:" + patientId + ":records");
```

## 4. Проектирование rate limiting

### Endpoints с ограничением
- `GET /api/v1/patients/search` — риск перегрузки индексов при переборе параметров
- `GET /api/v1/patients/{id}/records` — ресурсоёмкие JOIN-запросы, риск истощения пула соединений БД

### Алгоритм: Fixed Window Counter
- Ключ формируется как `rl:{endpoint}:{client_ip}`
- Счётчик запросов инкрементируется в памяти
- При достижении лимита в рамках окна запрос блокируется
- Окно автоматически сбрасывается по истечении TTL (60 секунд)
- Преимущества: O(1) сложность, минимальное потребление памяти, предсказуемое поведение

### Лимиты
| Категория пользователя | Поиск пациентов | История записей |
|-----------------------|-----------------|-----------------|
| Обычный | 60 запросов/мин | 100 запросов/мин |
| Врач/премиум | 300 запросов/мин | 500 запросов/мин |

> Примечание: разделение по ролям реализовано через параметр `limitOverride`, значение передаётся в зависимости от роли из JWT-токена.

## 5. Реализация rate limiting

### Интеграция в обработчики
Проверка лимита выполняется в начале `handleRequest`, до обращения к сервисному слою:
```cpp
auto rlResult = g_rateLimiter->check(rlKey);
if (!rlResult.allowed) {
    response.setStatusAndReason(HTTPResponse::HTTP_TOO_MANY_REQUESTS);
    // ... отправка ответа
    return;
}
```

### HTTP статус-коды и заголовки
- При превышении лимита возвращается `HTTP 429 Too Many Requests`
- В каждый ответ добавляются стандартные заголовки:
  - `X-RateLimit-Limit: 60`
  - `X-RateLimit-Remaining: 42`
  - `X-RateLimit-Reset: 38`
  - `Retry-After: 38` (указывается только при ответе `429`)

### Fail-open режим
При ошибке инициализации лимитера система продолжает работу без ограничений, чтобы не блокировать легитимный трафик.

## 6. Анализ производительности

### Влияние оптимизаций на систему
| Метрика | До оптимизации | После оптимизации | Комментарий |
|---------|---------------|-------------------|-------------|
| Время ответа (поиск, p95) | ~120 мс | ~8 мс | Доступ к памяти значительно быстрее сетевого запроса к БД |
| Нагрузка на БД | 100% | ~35-40% | Повторяющиеся запросы обслуживаются из кеша |
| Стабильность при всплесках | Падение p95 | p95 остаётся в норме | Rate limiting предотвращает перегрузку |



Формула:  
`Hit Rate = CACHE_HIT / (CACHE_HIT + CACHE_MISS) * 100%`
