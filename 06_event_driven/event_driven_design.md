# Проектирование Event-Driven архитектуры: Система медицинских записей

## 1. Анализ событий в системе

### Команды и соответствующие события
- POST /patients -> PatientRegistered
- POST /records -> MedicalRecordCreated
- PUT /records/{id} -> MedicalRecordUpdated
- PATCH /records/{id}/status -> MedicalRecordStatusChanged
- POST /records/{id}/assign -> DoctorAssignedToRecord

### Потребители событий
- PatientRegistered: сервис уведомлений, аналитика.
- MedicalRecordCreated: поисковый индекс, аналитика, аудит.
- MedicalRecordUpdated: поисковый индекс, сервис инвалидации кэша.
- MedicalRecordStatusChanged: сервис уведомлений, генератор отчётов, аудит.
- DoctorAssignedToRecord: сервис уведомлений, планировщик расписаний.

## 2. Проектирование Event-Driven архитектуры

### Производители событий
- Сервис управления медицинскими записями на POCO C++. Формирует события после успешной фиксации данных в основной базе.

### Потребители событий
- SearchIndexService: обновляет поисковый индекс для быстрого фильтра.
- NotificationService: отправляет email/SMS уведомления пациентам и врачам.
- AuditService: сохраняет историю изменений для соответствия нормативным требованиям.
- AnalyticsService: агрегирует метрики для дашбордов.

### Структура события
Событие сериализуется в UTF-8 JSON и содержит:
- event_id: уникальный идентификатор события.
- event_type: тип события.
- timestamp: время возникновения.
- aggregate_id и aggregate_type: идентификатор и тип доменного объекта.
- payload: полезные данные, специфичные для типа события.
- metadata: correlation_id, causation_id, идентификатор пользователя.

### Поток событий
1. Клиент отправляет HTTP-запрос.
2. API-сервис валидирует данные и сохраняет их в PostgreSQL.
3. После коммита транзакции сервис публикует событие в Kafka.
4. Брокер распределяет сообщение по партициям.
5. Подписанные сервисы потребляют событие и выполняют асинхронную обработку.

## 3. Проектирование взаимодействия через брокер сообщений

### Выбор брокера
Используется Apache Kafka. Выбор обоснован высокой пропускной способностью, возможностью хранения истории событий для аудита и нативным партиционированием, обеспечивающим порядок обработки данных одного пациента.

### Формат сообщений
Текстовый формат JSON в кодировке UTF-8. Схема событий эволюционирует за счёт опциональных полей, что обеспечивает прямую совместимость.

### Гарантии доставки
- Публикация: режим exactly-once достигается за счёт включения идемпотентности продюсера и параметра acks=all, требующего подтверждения от всех реплик брокера.
- Потребление: режим at-least-once реализуется через ручное подтверждение смещения после обработки. Дедупликация по event_id на стороне потребителя гарантирует идемпотентность бизнес-логики.

## 4. Применение паттерна CQRS

### Применимость
Паттерн CQRS применим, так как операции чтения (поиск записей, фильтрация по диагнозам) и записи (создание и изменение карт) имеют разные профили нагрузки и требования к индексации.

### Разделение моделей
- Write Model: нормализованная схема в PostgreSQL. Обеспечивает транзакционную целостность, строгую валидацию и публикацию доменных событий.
- Read Model: денормализованные индексы в Elasticsearch и кэш в Redis. Оптимизированы под быстрые выборки, полнотекстовый поиск и агрегации.

### Синхронизация моделей
События выступают механизмом асинхронной проекции. После публикации события MedicalRecordCreated сервис поискового индекса добавляет новый документ, а сервис кэша удаляет устаревшие ключи. Синхронизация происходит с задержкой, обеспечивая модель eventual consistency, что допустимо для аналитических и поисковых операций.

## 5. Реализация простого Event-Driven сервиса

### Инфраструктура
Развёртывание выполняется через Docker Compose. Среда включает контейнеры Zookeeper, Kafka, PostgreSQL и скомпилированное приложение на POCO C++.

### Producer
Сервис на C++ использует библиотеку librdkafka. После сохранения записи в базу данных создаётся объект события, сериализуется в JSON и публикуется в топик medical_records_events. Ключ партиционирования устанавливается равным patient_id для сохранения порядка событий одного пациента.

### Consumer
Сервис на C++ подписывается на топик в составе группы потребителей. Каждое сообщение парсится, проверяется на уникальность по event_id, после чего передаётся в соответствующий обработчик. Смещение подтверждается вручную только после успешной обработки.

### Тестирование
Для проверки запускается демонстрационный исполняемый файл, который публикует тестовое событие и ожидает его обработки консьюмером. Успешная доставка проверяется через встроенный консольный инструмент Kafka или веб-интерфейс управления кластером.

## 6. Примечание по терминологии оценки
В критериях оценивания упоминаются exchange и routing key. В архитектуре Apache Kafka эти концепции заменяются топиками (логические каналы) и ключами партиционирования (определяют распределение сообщений). Потребление организуется через группы потребителей, которые конкурируют за сообщения из партиций топика.
